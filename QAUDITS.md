This plan includes the same naming crosswalk, directory/file inventory, source/destination lineage, and metrics model used by QAUDITS and the style/universal layer so that no file, directory, or category is silently omitted. Local scans, historical snapshots, user-supplied documents, and remote observations are separate scopes and must never be added together as if they shared one denominator.

### State, denominator, and percentage rules

- Use `discovered`, `mapped`, `test_verified`, `hook_reviewed`, `local_verified`, `remote_verified`, `blocked`, `unknown`, and `not_applicable` as distinct states. Never promote a state because a filename, heading, percentage, or code symbol exists.
- Every ratio reports numerator, denominator, source manifest, scope, timestamp, and formula. For example, test-mapping coverage is `features with an applicable mapped test / registered feature requirements`; passing-test rate is `passed tests / executed tests`. These are different measures.
- A zero or unknown denominator produces `not_applicable` or `unknown`, never `100%`. Skipped, stale, inaccessible, and unreadable sources stay visible in the denominator policy and blocker list.
- Financial/trading measurements must include units, currency, period, data timestamp, venue/account scope, fees/slippage policy, and reconciliation provenance. Missing or stale source data blocks the metric and any dependent automation; “no trade” is a valid measured decision, not missing activity.
- Qtrade scorecards are per strategy, asset, timeframe, exchange, account mode (backtest/out-of-sample/walk-forward/paper/live), and evaluation period. Confidence scores require calibration against comparable historical outcomes; risk limits and security failures are hard gates rather than weights in a blended score. Separate simulated and live results, include costs/taxes where applicable, and report backtest-to-live degradation. Exchange capability counts do not enable an exchange or authorize deposits, transfers, leverage, or live order routing.
- Aggregate percentages only when the constituent populations and definitions are identical. Keep per-repository, per-ref, per-platform, per-app, per-suite, and per-strategy results available; do not mix historical and active scopes.
- Never convert local validation into remote proof, a workflow dispatch into a terminal result, a candidate into a replacement, or a passing metric into authorization for financial, protected-branch, release, or deployment actions.

### Per-document Markdown metrics, evolution, and model replacement

The repository-surface and sentence audits emit path/hash/scope-bound counts per parseable Markdown document: bytes, lines, words, heuristic sentences, headings, local/external link candidates, images, fenced code blocks and lines, inline-code spans, command candidates, instruction-candidate lines, and explicit `Feature:`/`Capability:` declarations. Evolution and QVillage/model-comparison candidate-line counts are also recorded. The gzip JSONL manifest reports the discovered Markdown denominator, metrics-computed documents, and documents without metrics separately. These are deterministic syntactic counts; sentence splitting, shell-command recognition, feature declarations, and content families are heuristics, not semantic validation. No source prose is persisted in these metric rows. `ALLMDFILESREFS.md` receives the richer metrics on its supported refresh path; documentation edits do not mean that every Markdown document was rewritten.

`ollamatracks/qaudits_evolution_plan.json` inventories evolution/QVillage/model-comparison documents by active versus historical/archive scope, source SHA-256, candidate lines, and explicit feature declarations. Model replacement assessment is deliberately review-only. A candidate comparison must use a matched, versioned benchmark and data/environment hashes, at least three replicated runs, at least 30 samples per required dimension and feature, non-overlapping confidence intervals showing QMOI strictly better on every required quality/safety/privacy/security/reliability/performance/resource/offline dimension, full canonical feature-registry coverage, all hard safety/license/regression/rollback gates, and independent review. Missing evidence, a tie, or any regression blocks eligibility. Even a complete local record is only `ELIGIBLE_FOR_INDEPENDENT_REVIEW`: it does not prove remote completion, authorize replacement, update a model selector, or count as a replaced model. QAUDITS always reports `models_replaced_count=0` unless a separate independently verified lineage artifact is supplied; the current planner never performs model replacement.

Content-safety requirements must be measured independently from document mentions: avoid unsolicited or user-prohibited sexual/pornographic and disturbing content, and block assistance that facilitates criminal conduct for every user. A role or claimed master identity must not bypass law, platform safeguards, or safety refusals. Current Markdown inventories do not constitute a production content classifier or enforcement proof; record classifier coverage, false-positive/negative tests, refusal outcomes, appeals/review, and authorization evidence as `NOT_MEASURED` until implemented and tested.

## Remote completion: required evidence and execution order

QAUDITS is the evidence coordinator, not an alternate authority for GitHub, Ollama, QMOI, or Copilot Chat. A local command can inventory requirements, prepare bounded actions, run permitted local checks, and collect read-only diagnostics. It cannot mint credentials, grant itself authority, dispatch a protected workflow without authorization, or claim that an autonomous agent completed work merely because it was invoked or its health endpoint responded.

Before reporting completion, build a gate matrix per repository and exact ref/SHA. Every row carries the correlation ID, operation/endpoint class, evidence source, observation time, verification level, result, and blocker/next action. Required gates include:

1. **Source and policy:** authenticated actor and credential role (value-free), root and scoped instruction inventories, applicable policy hashes, repository identity, dirty-tree state, and exact source SHA. Presence of a secret is not authentication.
2. **Protected-action authority:** current branch protection/ruleset, required reviews/checks, allowed workflow trigger, least-privilege scope, and explicit user/owner authorization. HTTP 401/403/404/409/422/429/5xx outcomes stay separately classified; ambiguous access errors are not converted to missing-resource or pass.
3. **Local requirements map:** stable requirement IDs linked to source implementation, owning test(s), workflow/event/hook, user documentation, category, owner, and source-manifest hash. Filename/keyword candidates remain `discovered`.
4. **Ollama run identity and completion:** target-owned workflow/run ID, triggering repo/ref/SHA, terminal conclusion, every job/step result, bounded action queue, remaining pending/blocked actions, generated artifacts and hashes, and independent post-run readback. A queued/accepted dispatch or a live heartbeat is not a completed run.
5. **Validation:** focused and full test suites, skipped/failed/unavailable cases, lint/type/build/package/install/runtime evidence, security/dependency/secrets checks, exact-SHA binding, and artifact provenance. Record commands/workflow IDs and terminal results, not just pass percentages.
6. **All ref/PR/history coverage:** branch/tag/ref inventories for both repositories, remote SHA/tree digests, PR and review state, merge ancestry, and reachable/intermediate commit trees. State excluded refs, unavailable APIs, inaccessible history, and shard gaps. A checkout scan never proves all remote history.
7. **Cross-repository parity:** independently read back each required ref in every target repository; compare exact commit and tree IDs and required evidence-document hashes. Fast-forward-only rules remain in force; divergence is a blocker, never permission to mirror or force-push.
8. **Release lifecycle:** source SHA, tag/release ID, terminal build/publish workflow, artifact names and SHA-256 values, retrieval from the remote release, install/runtime verification, deployment target/health, and rollback evidence. Distinguish `prepared`, `built`, `published`, `retrieved`, `installed`, and `deployed`; each needs its own evidence.
9. **Operational documentation:** compare expected documentation targets against the discovered Markdown inventory and update only defined agent-managed sections. Any human-authored text change needs review; report missing/stale/out-of-scope docs rather than silently fabricating content.
10. **Final readback and Q-version:** re-fetch target-owned terminal checks and refs after operations; bind lifecycle records and complete QAUDITS manifests to the exact resulting SHAs; require zero missing mandatory gates, no pending/blocked actions, and authorized finalization. Preserve an explicit `BLOCKED` result otherwise.

An exact-SHA workflow row is admissible only when it carries the canonical owner/repository, full `refs/heads/<branch>`, valid 40-character remote ref SHA, independently verified repository identity, workflow run ID, workflow head SHA equal to the ref SHA, `status=completed`, and `conclusion=success`. Re-fetch the ref after the run and bind the final SHA/tree to the required documents and artifacts. A name match, local HEAD match alone, queued/in-progress run, missing ID, branch mismatch, or dispatch response is not terminal proof. The local live verifier applies these checks to the requested branch; broader all-ref/PR/intermediate-tree and two-repository gates still require target-owned evidence for every required scope.

Use bounded deterministic shards for remote refs, PRs, commit trees, releases, and package catalogs. Each shard records exact input bounds, repo/ref/tree, worker/schema version, counts, unavailable/rate-limited paths, digest, and terminal status. Resume only a completed shard with matching inputs. Parallelize independent read-only shards and local validation; serialize mutations, lifecycle transitions, documentation publication, and ledger writes. Retry transient reads a bounded number of times. Never retry authorization failures into success.

The QAUDITS universe builds `audit_queue` from every indexed path after completing inventory. Deterministic, versioned rules prioritize inaccessible/metadata-only inputs, security and authorization, real-funds surfaces, release/workflow surfaces, test mappings, and memory/QSeed/recovery surfaces; all remaining paths retain a pending baseline-review item. The queue binds path hashes and source-manifest digest, records reasons and score, and uses stable path tie-breaking. Queue ordering prioritizes follow-up only: it never narrows the inventory denominator, drops a path, or sets semantic, implementation, test, or remote status to pass. Recompute the queue when its source manifest or policy version changes.

Model-assisted deep-learning review is an optional candidate generator, not the audit authority. If enabled, it must run on an explicitly approved local inference endpoint by default, use bounded batches and timeouts, bind results to source hashes/model/prompt versions, label suggestions as unverified, and never emit a pass or apply code changes. Do not send repository content to an external model without separately authorized data review. Unknown model identity, endpoint, stale inputs, rate limits, and inference errors remain blocked evidence. ## Large-repository execution and completeness controls

The QAUDITS universe uses a deterministic path-enumeration pass, followed by bounded parallel file hashing/content inspection in fixed-size batches. Worker count is capped, batch memory is bounded, and results are merged in stable path order. Full-file SHA-256 is streamed so a very large file can still be identified without loading it into memory; content-derived classification for files above the configured parse limit remains explicitly `metadata_only` and contributes an unavailable-content blocker. Hash/read errors and symlinks are surfaced rather than silently dropped. Excluded dependency/build/cache roots are listed in the manifest as policy exclusions, not counted as scanned coverage. Mutable self-referential outputs (`oe2.txt`, `remotecompletion.md`, `remote-completion.json`, `remote-evidence-ledger.jsonl`, telemetry, and generated QAUDITS artifacts) are reported by path as explicit exclusions so writing the evidence cannot silently stale its own source manifest; their contents are validated separately. Historical/archive paths retain their source scope in canonical records and are not relabeled as active implementation.

For multi-repository or very large history audits, use shardable immutable inputs keyed by repo/ref/commit tree and stable path prefix. Each shard must emit input bounds, counts, bytes, skipped/unavailable paths, category and extension histograms, manifest hash, worker/version, timings, and a completion marker. Merge shards only after checking for missing/overlapping path ranges and duplicate source IDs; verify the merged manifest against a deterministic root digest. Resume only completed matching shards; changed refs, worker/schema versions, or source hashes invalidate prior shard evidence. Keep retries bounded, checkpoint them, and prioritize security, critical product paths, lifecycle prerequisites, then remaining exhaustive work without marking unfinished shards complete.

Parallel work must not introduce race-based false confidence. Workers are read-only during discovery, write distinct temporary outputs, and publish via atomic replacement after verification. Lifecycle evidence and ledger writes remain serialized and hash-chained. Remote reads are rate-limited, endpoint/status-classified, cached only with explicit TTL and ETag/SHA binding, and refreshed before protected decisions. No concurrency setting, cache hit, partial shard, timeout, or cancelled worker may produce a `PASS`.

### Time-bounded execution and honest acceleration

Optimize time-to-actionable-evidence, not by weakening coverage gates. Order safe work by dependency and risk: policy/security/authorization blockers first, then critical production and lifecycle paths, then independent product surfaces. Run independent read-only shards and local validations concurrently under explicit CPU, memory, I/O, and API limits; serialize writes, release/merge/deploy actions, and correlated evidence updates. Each shard publishes input ref/tree, stable path range, counts/bytes, skipped/unavailable rows, schema/worker versions, duration, and digest, and is reusable only when all source identities match. Changed refs, schema, filters, or input digests invalidate the shard.

Report cold-scan and warm-resume time separately, including enumeration, hashing, parsing, document refresh, test, remote API, and final-readback durations. Never translate a time budget, prioritization, cache hit, parallel worker completion, partial shard, or bounded run into a completeness claim. Large or multi-year scopes may require multiple target-owned jobs; do not promise completion in minutes where exhaustive histories, external approvals, unavailable files, security findings, or human semantic review remain. The exit condition is complete independently verified gates—or a terminal, prioritized blocker queue that names every unfinished gate and its evidence/authority prerequisite—not elapsed time.
